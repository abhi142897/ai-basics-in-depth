LangGraph

LangGraph is a low-level orchestration framework and runtime for stateful agents. You describe your agent as a graph — shared state, nodes that do work, and edges that decide what runs next — and LangGraph gives you the hard production features for free: saved progress, pausing for a human, streaming, retries and resuming after a crash.

If create_agent (Topic 04) is the automatic gearbox, LangGraph is the manual one with the whole engine exposed. In fact create_agent is a LangGraph graph under the hood, so everything on this page also explains how your LangChain agents actually run. The code samples were run against langgraph 1.2 (state and reducers, conditional edges, checkpoints, interrupt + resume, Send, Command, the Store).

Why graphs?

A plain while-loop agent (Topic 01) is fine until real requirements arrive:

  • "Pause here and wait for a manager to approve — maybe for three days." A Python loop can't wait that long.
  • "If the server crashes at step 7 of 12, don't start over." A loop in memory is gone.
  • "Run these three checks in parallel, then merge." Needs real orchestration.
  • "Always do A, then B; only the middle step should be up to the model." Hard to enforce inside a free-running loop.

A graph makes the control flow explicit and inspectable. You decide which parts are fixed code paths and which parts the model is free to steer — the workflow-versus-agent dial from Topic 01, but as something you can draw, test and resume.

LangGraph does not hide prompts or force an "agent architecture" on you. It is plumbing for durable, controllable execution. That makes it more work than create_agent — and more powerful.

The three core ideas: State, Nodes, Edges

ConceptWhat it isIn code
StateThe shared data every node reads and updates — the graph's memory for this runA TypedDict (or Pydantic model)
NodeOne step of work: takes the current state, returns updates to itA normal Python function
EdgeWhich node runs next — fixed, or chosen at run time ("conditional")add_edge, add_conditional_edges
START→ agentnode: call the LLM? → toolsnode: run tool calls↺ agent END

Execution is a series of "super-steps": run the nodes that are ready, merge their updates into state, pick the next nodes by following edges, repeat until END. After every super-step, LangGraph can save a checkpoint of the state — the source of its durability.

State and reducers

State is declared as a typed schema. Each key can have a reducer — a rule for how new values merge with old ones. With no reducer a key is simply overwritten; with one, updates accumulate.

Python
import operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph.message import add_messages

class SupportState(TypedDict):
    messages: Annotated[list, add_messages]     # reducer: append/merge messages by id
    refund_total: Annotated[float, operator.add]  # reducer: sum every update
    status: str                                  # no reducer: last write wins

Nodes return only the keys they change — a partial update:

Python
def mark_resolved(state: SupportState) -> dict:
    return {"status": "resolved"}               # messages and refund_total untouched

Why reducers matter: two nodes running in parallel can both add to messages or refund_total without overwriting each other. For the very common "chat history" case LangGraph provides a ready-made MessagesState with messages and add_messages already wired.

Your first graph

No LLM yet — just to see the moving parts:

Python
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    text: str

def shout(state: State) -> dict:
    return {"text": state["text"].upper()}

def add_bang(state: State) -> dict:
    return {"text": state["text"] + "!"}

builder = StateGraph(State)
builder.add_node("shout", shout)
builder.add_node("bang", add_bang)
builder.add_edge(START, "shout")
builder.add_edge("shout", "bang")
builder.add_edge("bang", END)

graph = builder.compile()                 # validates structure, returns a runnable
print(graph.invoke({"text": "hello"}))    # {'text': 'HELLO!'}

The pattern is always: define state → add nodes → wire edges → compile() → invoke/stream. The compiled graph is a standard LangChain runnable, so it has invoke, stream and batch, and it can even be used as a node inside another graph.

Conditional edges — building an agent from scratch

A conditional edge calls a small router function that looks at the state and returns the name of the next node. That one feature turns a pipeline into an agent loop. Here is the whole Acme agent, no create_agent:

Python
from langchain.chat_models import init_chat_model
from langchain_core.messages import ToolMessage
from langgraph.graph import StateGraph, MessagesState, START, END

tools = [get_order, issue_refund]                 # @tool functions from Topic 04
tools_by_name = {t.name: t for t in tools}
model = init_chat_model("anthropic:claude-sonnet-5-5").bind_tools(tools)

def call_model(state: MessagesState) -> dict:
    return {"messages": [model.invoke(state["messages"])]}

def run_tools(state: MessagesState) -> dict:
    outputs = []
    for call in state["messages"][-1].tool_calls:
        result = tools_by_name[call["name"]].invoke(call["args"])
        outputs.append(ToolMessage(content=str(result), tool_call_id=call["id"]))
    return {"messages": outputs}

def route(state: MessagesState) -> str:
    return "tools" if state["messages"][-1].tool_calls else END

builder = StateGraph(MessagesState)
builder.add_node("agent", call_model)
builder.add_node("tools", run_tools)
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", route, ["tools", END])
builder.add_edge("tools", "agent")                # the loop-back edge
graph = builder.compile()

Read it against the loop from Topic 01 — call_model is "model decides", run_tools is "act + observe", route is "repeat or stop". Once the loop is yours you can insert anything: a "check policy" node before refunds, a "summarise" node when messages get long, a "notify customer" node at the end.

A workflow with a model-steered middle

classifyalways first→ agent loopmodel decides→ policy checkalways, in code→ send reply

This is the sweet spot: guarantees where you need them, flexibility where you want it. A pure prompt can only ask the model to always run the policy check; a graph makes it impossible to skip.

Persistence: checkpoints, threads, time travel

Pass a checkpointer to compile() and LangGraph saves the state after every super-step, grouped under a thread id.

Python
from langgraph.checkpoint.memory import InMemorySaver

graph = builder.compile(checkpointer=InMemorySaver())    # use a DB-backed saver in production
cfg = {"configurable": {"thread_id": "case-1042"}}

graph.invoke({"messages": [("user", "Order 1042 is late")]}, cfg)
graph.invoke({"messages": [("user", "Also, can you email me the receipt?")]}, cfg)  # same thread: remembers

snapshot = graph.get_state(cfg)              # current state + which node runs next
for s in graph.get_state_history(cfg):       # every past checkpoint
    print(s.next, s.values["messages"][-1])

This one feature unlocks four capabilities:

  • Conversation memory — a thread is a conversation.
  • Fault tolerance — after a crash, re-invoke the same thread and execution resumes from the last good checkpoint.
  • Human-in-the-loop — the run can stop, sit saved for days, then continue (next section).
  • Time travel — inspect any past step, edit the state, and re-run from there to debug "what if the model had seen X?".

The idempotency warning

When a node is retried or resumed, it may run again. If it already called issue_refund, you can refund the customer twice. Make side-effecting tools idempotent — e.g. pass an idempotency key like refund-1042 that the refund API de-duplicates — or put the side effect in its own node so a checkpoint lands right after it.

Human-in-the-loop with interrupt()

Calling interrupt(...) inside a node pauses the graph, saves state, and hands a payload back to the caller. The graph then waits — as long as needed — until someone resumes it with a value.

Python
from langgraph.types import interrupt, Command

def approve_refund(state: SupportState) -> dict:
    decision = interrupt({
        "question": "Approve this refund?",
        "order_id": "1042",
        "amount": 84.50,
    })                                           # <-- graph stops here
    if decision == "approve":
        return {"status": "approved"}
    return {"status": "rejected"}

# ---- first call: runs until the interrupt ----
cfg = {"configurable": {"thread_id": "case-1042"}}
result = graph.invoke({"messages": [("user", "Refund order 1042")]}, cfg)
print(result["__interrupt__"])                   # the payload shown to the human

# ---- later (minutes or days), a human decides ----
graph.invoke(Command(resume="approve"), cfg)     # same thread id -> continues
run until interruptstate saved to the checkpointer
⏸ pausedno process running, no cost
human reviewsapprove / reject / edit
Command(resume=…)same thread → continues from that node

One subtle rule: on resume the node restarts from its beginning and interrupt() now returns the human's answer. So keep code before an interrupt() free of side effects (or idempotent). HumanInTheLoopMiddleware in Topic 04 is a convenience wrapper over exactly this mechanism.

Streaming

Agents are slow; users hate staring at a spinner. LangGraph streams in several modes you can combine:

  • "values" — the full state after each step.
  • "updates" — just the delta each node produced (easy progress UI: "looking up order…").
  • "messages" — LLM tokens as they are generated.
  • "custom" — anything you emit yourself from inside a node.
Python
for mode, chunk in graph.stream(
    {"messages": [("user", "Where is order 1042?")]},
    cfg,
    stream_mode=["updates", "messages"],
):
    print(mode, chunk)

Parallelism and fan-out / fan-in

If a node has two outgoing edges, both targets run in the same super-step, in parallel; a downstream node with two incoming edges waits for both. For "do the same thing N times where N is only known at run time" (map-reduce) use the Send API:

Python
from langgraph.types import Send

class BatchState(TypedDict):
    order_ids: list[str]
    results: Annotated[list, operator.add]       # reducer merges the parallel outputs

def fan_out(state: BatchState):
    return [Send("check_order", {"order_id": oid}) for oid in state["order_ids"]]

def check_order(args: dict) -> dict:
    return {"results": [f"{args['order_id']}: ok"]}

builder = StateGraph(BatchState)
builder.add_node("check_order", check_order)
builder.add_conditional_edges(START, fan_out, ["check_order"])
builder.add_edge("check_order", END)

Typical uses: check 50 orders at once, run several retrievers and merge, or have three "reviewer" nodes critique a draft simultaneously.

Subgraphs and multi-agent graphs

A compiled graph can be a node inside another graph (a subgraph), which is how you compose bigger systems from tested pieces. For multi-agent designs LangGraph gives you the routing primitive: a node returns a Command that both updates state and says where to go next.

Python
from typing import Literal
from langgraph.types import Command

def triage(state: SupportState) -> Command[Literal["billing_agent", "shipping_agent"]]:
    topic = classify(state["messages"][-1].content)      # your LLM or rules
    return Command(
        goto="billing_agent" if topic == "billing" else "shipping_agent",
        update={"status": f"routed to {topic}"},
    )
Supervisortriage→ Billing agentown tools + prompt Shipping agentown tools + prompt → Merge & reply

Same shapes as Topic 01 (supervisor, handoff, sub-agent) — now each one is just nodes and edges you can see, test and trace.

Long-term memory: the Store

Checkpoints are scoped to a thread. To remember things across threads — "this customer prefers email" — LangGraph has a separate Store: a namespaced key-value store (with optional semantic search).

Python
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()                         # swap for a persistent store in production
graph = builder.compile(checkpointer=InMemorySaver(), store=store)

ns = ("customers", "cust-77")                   # namespace: like a folder path
store.put(ns, "prefs", {"channel": "email", "tone": "brief"})
print(store.get(ns, "prefs").value)

Nodes can read and write the store during a run, so the agent starts conversation #2 already knowing what it learned in conversation #1.

Running it for real

  • LangGraph Studio / dev server — a local UI to run a graph, watch state change step by step, and replay from any checkpoint. Invaluable for learning.
  • LangGraph Server / platform — hosted or self-hosted runtime exposing your graph over an API with persistent checkpoints, background runs and scheduling. Check the current docs for deployment options.
  • LangSmith — traces every node and LLM call, so a bad run can be inspected and turned into an eval case (Topic 07).
  • Durable checkpointers — Postgres/SQLite/etc. instead of InMemorySaver once you leave your laptop.

When to use LangGraph (and when not to)

SituationReach for
One agent, some tools, a few guardrailscreate_agent + middleware
Mandatory steps around a model-driven coreLangGraph
Approvals that may wait hours or daysLangGraph (interrupt + durable checkpointer)
Parallel branches, map-reduce, cycles you controlLangGraph
Several specialised agents cooperatingLangGraph (supervisor / handoffs)
Long-running, planning-heavy, file-using agentA harness like Deep Agents (Topic 06), which itself runs on LangGraph
Straight-line prompt pipelineLCEL or plain code — a graph is overkill
Mental model: LangChain gives you the parts, LangGraph runs them durably. Use LangChain primitives (models, tools) inside LangGraph nodes — they are designed to work together.
