LangChain

LangChain is an open-source framework for building LLM applications and agents. It gives you a standard interface over hundreds of model providers and tools, plus create_agent — a few-line way to get a working tool-calling agent. Since the 1.0 release (October 2025) it is a much smaller, sharper library than the sprawling "chains for everything" framework many older tutorials describe.

Topic 02 showed the raw mechanics; LangChain is what stops you rewriting them for every provider.

Heads-up: a lot of LangChain content online is from the pre-1.0 era (LLMChain, initialize_agent, AgentExecutor). That style is legacy — if a tutorial uses it, look for the 1.0 equivalent on this page. Verify exact signatures against docs.langchain.com, since the library keeps evolving.

Where LangChain fits: framework, runtime, harness

The LangChain ecosystem has several pieces and people mix them up constantly. The docs themselves describe a useful three-layer view:

LayerProductWhat it gives you
FrameworkLangChainModel/tool abstractions, create_agent, middleware, integrations
RuntimeLangGraphDurable execution, state, persistence, human-in-the-loop (Topic 05)
HarnessDeep AgentsBatteries-included agent: planning, filesystem, sub-agents, context management (Topic 06)
Observability & evalsLangSmithTracing, datasets, evaluations, monitoring (Topics 07, 08)
LangChainbuild it fastruns on → LangGraphdurable runtimewatched by → LangSmithtraces & evals

Important: LangChain 1.0's create_agent is built on top of LangGraph. So LangChain is the high-level, ergonomic layer and LangGraph is the low-level engine underneath. You can start high and drop down when you need more control — and your agent is a LangGraph graph either way.

What changed in 1.0

  • create_agent is the standard way to build agents (replacing create_react_agent and the old agent executors).
  • Middleware lets you hook into every step of the loop.
  • Standard content blocks give one provider-neutral format for text, reasoning, citations and tool calls.
  • Structured output is part of the main agent loop (fewer extra LLM calls).
  • Legacy chains and old APIs moved to a langchain-classic package; the 1.0 line promises no breaking changes until 2.0.

Chat models: one interface, many providers

The first thing LangChain gives you is a uniform way to talk to models. init_chat_model takes a "provider:model" string and returns an object with the same methods regardless of vendor — so swapping models is a one-line change.

Python
from langchain.chat_models import init_chat_model

model = init_chat_model("anthropic:claude-sonnet-5-5")     # or "openai:...", "google_genai:..."

reply = model.invoke("In one line: what is an AI agent?")
print(reply.content)

# Same object can stream tokens as they arrive
for chunk in model.stream("Explain MCP in two sentences."):
    print(chunk.content, end="")

# And run many prompts concurrently
answers = model.batch(["Define RAG.", "Define LCEL."])

Every runnable thing in LangChain exposes the same trio: invoke (one input → one output), stream (output as it's produced), batch (many inputs). Learn these three and you can use any component.

Messages are typed objects — SystemMessage, HumanMessage, AIMessage, ToolMessage — which map one-to-one onto the roles from Topic 02, so you can also pass plain {"role": "...", "content": "..."} dicts.

Prompts, parsers and the | pipe (LCEL)

For fixed pipelines — no tool loop — LangChain still offers the LangChain Expression Language (LCEL): chain components with the | operator, like Unix pipes.

Python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_messages([
    ("system", "You classify support emails. Reply with one word: refund, shipping or other."),
    ("human", "{email}"),
])

chain = prompt | model | StrOutputParser()

chain.invoke({"email": "My package is 8 days late, I want my money back"})
# -> "refund"
{"email": "..."}input dict| Promptfills the template| Modelgenerates| Parser"refund"

The chain is itself a runnable, so it also has invoke/stream/batch, and you can nest chains inside chains. LCEL is great for the workflow patterns from Topic 01 (chaining, routing, parallel branches). When the path isn't fixed and the model should loop on tools, use create_agent instead; when you need branching, cycles or persistence, use LangGraph.

Defining tools

A tool in LangChain is just a Python function with the @tool decorator. The function name becomes the tool name, the docstring becomes the description, and the type hints become the input schema — the same three things from Topic 02, generated for you.

Python
from langchain.tools import tool

@tool
def get_order(order_id: str) -> dict:
    """Look up an order by its 4-digit id. Use this first for any order question."""
    return {"status": "in_transit", "eta": "2026-09-28", "total": 84.50}

@tool
def issue_refund(order_id: str, amount: float, reason: str) -> str:
    """Refund an order. Only call after confirming it is late or damaged.
    reason must be one of: late, damaged, wrong_item."""
    return f"Refunded ${amount:.2f} for order {order_id}"

Tool descriptions are prompt text — write them with the care you'd give a system prompt. Tools can also come from MCP servers (see langchain-mcp-adapters in Topic 03) or from LangChain's large catalogue of integrations (search, databases, browsers, …).

create_agent — the standard way to build an agent

Python
from langchain.agents import create_agent

agent = create_agent(
    model="anthropic:claude-sonnet-5-5",
    tools=[get_order, issue_refund],
    system_prompt=(
        "You are Acme's support agent. Check the order before refunding. "
        "Never refund more than the order total."
    ),
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "Order 1042 is late - refund me please."}]}
)
print(result["messages"][-1].content)       # the final answer

That is a full tool-calling agent: it loops model → tools → model until the model stops asking for tools, exactly the loop from Topic 01. The input and output are a dict with a messages list — the agent's state.

What's inside the loop

Start→ Model nodedecide: answer or tools?→ Tools noderun each requested tool↺ Endwhen no tool calls

You can watch it work by streaming, which yields each step as it happens (great for UIs and debugging):

Python
for step in agent.stream(
    {"messages": [{"role": "user", "content": "Where is order 1042?"}]},
    stream_mode="updates",            # one chunk per node that ran
):
    print(step)
  • stream_mode="values" — full state after each step.
  • stream_mode="updates" — only what each node changed.
  • stream_mode="messages" — LLM tokens as they are generated (typing effect).

Structured output

Want the agent's final answer as typed data instead of prose? Pass a Pydantic model as response_format. LangChain picks the best mechanism for your provider (native structured output when available, otherwise a forced tool call) and puts the parsed object in the result.

Python
from pydantic import BaseModel

class Resolution(BaseModel):
    order_id: str
    action_taken: str          # e.g. "refunded", "none"
    refund_amount: float
    customer_message: str

agent = create_agent(
    model="anthropic:claude-sonnet-5-5",
    tools=[get_order, issue_refund],
    response_format=Resolution,
)
out = agent.invoke({"messages": [{"role": "user", "content": "Order 1042 is late, refund me."}]})
print(out["structured_response"])      # Resolution(order_id='1042', action_taken='refunded', ...)

This is how an agent hands a clean result to the next program in your pipeline — a database write, a ticket update, another agent.

Middleware — hooks into the loop

Middleware is LangChain 1.0's headline feature. It lets you intercept and change what happens at each point of the agent loop without rewriting the loop — a cleaner home for the production concerns that used to bloat prompts and glue code.

before_modeltrim history, redact PII, inject context
wrap_model_callswap model, add retries or fallbacks, change tools
after_modelvalidate output, require approval of tool calls
wrap_tool_calllog, retry, block, or rewrite each tool execution

Built-in middleware

  • Human-in-the-loop — pause before chosen tools run and wait for approve / edit / reject.
  • Summarization — compact old messages automatically when the conversation gets long.
  • PII — redact, mask or block sensitive data like emails and card numbers.
Python
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware, PIIMiddleware
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model="anthropic:claude-sonnet-5-5",
    tools=[get_order, issue_refund],
    middleware=[
        PIIMiddleware("email", strategy="redact"),                 # hide emails from the model
        HumanInTheLoopMiddleware(interrupt_on={"issue_refund": True}),   # a human approves refunds
    ],
    checkpointer=InMemorySaver(),      # HITL needs saved state so it can pause and resume
)

And a tiny custom one — log every tool call (this is the shape of most custom middleware):

Python
from langchain.agents.middleware import wrap_tool_call

@wrap_tool_call
def log_tool_calls(request, handler):
    print("TOOL:", request.tool_call["name"], request.tool_call["args"])
    return handler(request)            # let the real tool run

agent = create_agent(model="anthropic:claude-sonnet-5-5",
                     tools=[get_order, issue_refund],
                     middleware=[log_tool_calls])

Why this matters: middleware is a lightweight, built-in harness (Topic 06). Context trimming, approvals and guardrails — the things that make agents dependable — plug in here.

Memory: threads and checkpointers

By default each invoke starts fresh. To make the agent remember a conversation, give it a checkpointer and call it with a thread id:

Python
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent("anthropic:claude-sonnet-5-5", [get_order], checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "customer-77"}}

agent.invoke({"messages": [{"role": "user", "content": "My order is 1042."}]}, cfg)
agent.invoke({"messages": [{"role": "user", "content": "Where is it?"}]}, cfg)   # remembers 1042

InMemorySaver is for learning; in production you swap in a database-backed checkpointer (Postgres, SQLite, …) so memory survives restarts. For long-term memory across threads there is a separate store interface — covered with LangGraph in Topic 05.

Retrieval (RAG) in LangChain

LangChain ships the whole RAG toolbox as interchangeable parts:

  • Document loaders — PDFs, web pages, Confluence, Drive, …
  • Text splitters — cut documents into overlapping chunks.
  • Embeddings + vector stores — index chunks for similarity search.
  • Retrievers — a standard "give me relevant chunks for this query" interface.

The modern pattern is agentic RAG: wrap your retriever in a tool and let the agent call it when it needs facts.

Python
@tool
def search_policies(query: str) -> str:
    """Search Acme's support policies. Use for any question about refunds, returns or shipping rules."""
    docs = vector_store.similarity_search(query, k=3)
    return "\n\n".join(d.page_content for d in docs)

agent = create_agent("anthropic:claude-sonnet-5-5", [get_order, search_policies])

LangChain vs LangGraph vs plain SDK — which to reach for?

  • Start with create_agent for a standard tool-using agent. Add middleware for approvals, trimming and guardrails.
  • Drop to LangGraph when you need explicit branching, loops with your own routing, parallel steps, multiple cooperating agents, or fine control over state and persistence.
  • Use a harness (Deep Agents) when the task is long-running and needs planning, files and sub-agents out of the box.
  • Use the raw provider SDK if you have a single model, a few tools and want zero abstraction — the 15-line loop from Topic 01 is genuinely enough for many apps.
  • Don't adopt a framework just because it's popular; adopt it for the specific thing it saves you (provider portability, tracing, persistence, middleware).

Seeing what happened: LangSmith

Because every LangChain/LangGraph run is structured, LangSmith can trace it end-to-end: each model call, tool call, token count and latency in a tree you can click through. Turning it on is mostly a couple of environment variables (check the current docs for the exact names). You'll lean on it heavily for evals in Topic 07.
