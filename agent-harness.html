Agent Harness

A language model by itself isn't an agent. The thing that turns raw model intelligence into a dependable worker is the agent harness: all the code around the model — the loop, tools, permissions, context management, memory, sandbox, limits and logging. The compact formula people use is Agent = Model + Harness.

This is the topic where the earlier pages click together. Topic 01's loop, Topic 02's context window, Topic 03's tools and Topic 05's durable execution are all parts of a harness. And it is the answer to "why does the same model feel brilliant in one product and clumsy in another?" — usually, the harness.

Terminology warning: the word "harness" is used for two different things. This page is about the agent harness (runs the agent). Topic 07 uses eval harness (runs the tests). Same word, different jobs — you need both.

What a harness is — and isn't

Strip a coding assistant, a research agent or a support bot down and you find a model plus a lot of unglamorous engineering. If you are not the model, you are the harness.

That's the key insight: a harness is a reusable product, not just a pile of glue.

The model asks for things; the harness owns them. The model can request issue_refund, but it can't enforce the $200 rule against itself. Only the harness can — which is why safety-critical rules belong here and not in the prompt.

A tiny harness, in code

Here is the Topic 01 loop grown up into a harness. It's framework-free on purpose — read it as a list of responsibilities. (model, ask_human and log are assumed helpers.)

Python (sketch)
class Harness:
    def __init__(self, model, tools, rules, max_steps=25, max_tool_chars=4000):
        self.model, self.tools, self.rules = model, tools, rules
        self.max_steps, self.max_tool_chars = max_steps, max_tool_chars

    def run(self, goal):
        ctx = [SYSTEM_PROMPT, {"role": "user", "content": goal}]

        for step in range(self.max_steps):                 # LIMITS: bounded loop
            ctx = self.compact(ctx)                        # CONTEXT: keep the window healthy
            reply = self.model(ctx, tools=self.schemas())
            ctx.append(reply)
            log(step, reply)                               # OBSERVABILITY

            if not reply.tool_calls:
                return reply.text

            for call in reply.tool_calls:
                verdict = self.rules.check(call)           # PERMISSIONS: code, not prompt
                if verdict == "deny":
                    result = f"DENIED by policy: {self.rules.why(call)}"
                elif verdict == "ask" and not ask_human(call):
                    result = "Human rejected this action."
                else:
                    result = self.safe_run(call)           # TOOLS: errors become observations
                ctx.append(tool_message(call, self.truncate(result)))   # CONTEXT: cap size
        return "Stopped: step limit reached."

    def safe_run(self, call):
        try:
            return self.tools[call.name](**call.args)
        except Exception as e:
            return f"Error: {e}"

    def truncate(self, text):
        text = str(text)
        return text if len(text) <= self.max_tool_chars else text[: self.max_tool_chars] + "\n...[truncated]"

Notice what isn't there: any clever AI. Every line is ordinary engineering — and every line directly affects whether the agent is safe, affordable and reliable.

Tools in a harness: fewer, sharper, general

  • A shell and a filesystem are the most general tools — with bash + read/write/edit, a model can search code, run tests, transform data and inspect results without a bespoke tool per task. This is why coding agents generalise so well to other knowledge work.
  • Prefer fewer, well-designed tools. Several teams have reported better results after removing tools. Each tool costs context and adds a choice the model can get wrong.
  • Shape the output. Return what the model needs for its next decision — not the raw 10,000-line dump. Offer search/pagination instead.
  • Write errors for the model (what went wrong, what to try next).
  • Treat tool interfaces like a public API — models are often post-trained with a specific harness's tools in the loop, so changing a familiar tool's shape can hurt quality.
  • MCP (Topic 03) is how a harness plugs in third-party tools without custom code; the harness still decides which servers/tools are allowed.

Context engineering — the harness's hardest job

Topic 02 introduced the context window and context rot. A harness is where you actually manage it. The principle: find the smallest set of high-signal tokens that lets the model do the next step well.

TechniqueHow it worksTrade-off
Tool-result clearingOnce a result has been used, replace it with a short stubCheap and safe; model can re-fetch if needed
CompactionAs the window nears its limit, summarise history and continue with the summaryRisk: the summary drops a detail that mattered later
Structured notes / scratchpadAgent writes key facts to a file (notes.md) and re-reads itSurvives compaction and restarts; needs discipline
Just-in-time loadingKeep paths/IDs in context; load content only when neededMore tool calls, far fewer tokens
Sub-agentsDelegate a messy side-task to a fresh window; get back a short digestExtra cost; digest may omit nuance
Progressive disclosureShow a one-line menu; reveal full instructions only on demandNeeds good descriptions so the model picks right

Progressive disclosure in practice: skills

A neat modern pattern is the skill: a folder with a SKILL.md (plus optional scripts and reference files). At startup the harness loads only each skill's short name and description. When a task matches, the model reads the full SKILL.md; if that points to more files, those are read only if needed. You can ship dozens of capabilities without paying for them all in every request — the context equivalent of lazy loading.

Practical rule: every token in the window should earn its place. If the model doesn't need it for the next decision, it shouldn't be there.

Planning, to-do lists and delegation

For multi-step work, models drift. Harnesses counter that with structure:

  • A to-do / plan tool — the model writes its plan as a checklist and ticks items off. The list stays in context, which keeps it focused on the goal across dozens of steps (and shows the user progress).
  • A virtual or real filesystem — plans, drafts and findings live in files, not in the chat transcript.
  • Sub-agents — "research our refund policy" runs in an isolated context; only the conclusion returns. This keeps the main thread clean and allows parallel work.

Deep Agents (LangChain's harness) bundles exactly these: planning, a filesystem, sub-agent spawning and long-term memory, with LangGraph providing durable execution beneath.

Permissions, sandboxes and approvals

The more power an agent has, the more the harness must constrain it. Think in risk tiers:

TierExamplesPolicy
Read-only, low riskget_order, search policies, read fileAuto-allow
Reversible writesedit a draft, add an internal noteAllow, log, make undoable
Costly or external effectsissue_refund, send email, post a messageAsk a human (or threshold rules: auto under $200)
Destructive / sensitivedelete data, change permissions, spend money at scaleDeny by default, or require strong approval
  • Allow-lists beat block-lists. Enumerate the paths, commands and domains the agent may use.
  • Sandbox code execution — container or VM, no production secrets, restricted network, resource limits.
  • Hooks — run your code before/after tool calls to validate, block, or log (supported by several harnesses).
  • Human-in-the-loop — approve / edit / reject, ideally with a durable pause (Topic 05).
  • Don't rely on "please don't do X" in the system prompt for anything that matters — enforce it in code.

Long-running agents: surviving many context windows

Some jobs (build a feature, migrate a codebase, produce a research report) take hours — longer than any single context window. Engineering teams have converged on a pattern for this:

1. Initializer sessionsets up the environment, writes a feature list and a progress file
2. Work sessionfresh context: reads progress file + git log, does one item
3. Leave a clean statetests pass, commit, update the progress file
4. Next sessionstarts fresh again — memory lives in files and git, not the chat

The insight: the agent's memory is the filesystem, not the context window. Each session is like a new engineer arriving for a shift who reads the handover notes. Without this discipline, agents tend to try to do everything at once, run out of context mid-task, or declare victory early.

Reliability: limits, retries, checkpoints

  • Budgets: max steps, max tokens, max wall-clock time, max cost per run.
  • Loop detection: same tool + same args three times in a row → stop or change strategy.
  • Retries with backoff for flaky tools and rate limits; never blindly retry non-idempotent actions.
  • Checkpoint/resume so a crash at step 40 doesn't cost the first 39 (LangGraph does this for you).
  • Graceful failure: when stuck, escalate to a human with a clear summary instead of looping.

Observability

You cannot improve what you can't see. A good harness records, for every run, a trace: each model call (prompt, response, tokens, latency), each tool call (args, result, duration, errors), each permission decision and each compaction. These traces are the raw material for debugging and for evals (Topic 07) — every production failure should be convertible into a test case in one click.

Build your own vs use an existing harness

Use an existing harness when…Build / customise when…
Your task looks like coding, research or file-based knowledge workYou have strict domain rules or compliance needs
You want to ship quickly and inherit tested defaultsYou need tight control over cost, latency and tool set
You're happy to adopt its tool and permission modelYour tools are specialised (your own APIs, MCP servers)

Most real teams do both: start from an existing harness (Agent SDK, Deep Agents, …), then add their own tools, permission rules and evals on top.

A useful long-term view: as models improve, harnesses should get simpler. Scaffolding that once compensated for model weaknesses (forced planning steps, heavy prompt tricks) can become dead weight. Re-test your harness with each new model — and let your evals tell you what to delete.
