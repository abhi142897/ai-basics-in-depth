AI Agents — The Big Picture

An AI agent is a program where a language model decides, step by step, what to do next — which tool to call, what to read, when to stop — until a goal is done. Every other topic in the learning charter (MCP, LangChain, LangGraph, harnesses, evals) exists to make that one idea build-able, reliable and measurable.

This first page is the map. Read it before the others: the vocabulary here (loop, tool, state, workflow, harness, eval) is used on every later page.

Running example for all 8 pages — the "Acme Support Agent"

A customer writes: "Where is my order #1042? If it's late, please refund me." The agent can look up orders, check shipping, and issue refunds. We will keep coming back to this one agent so every concept has something concrete to attach to.

Why agents at all?

A plain LLM call is text in, text out. That is powerful, but it has hard limits:

  • It cannot do anything — it can write "I will refund you" but it cannot touch your refund system.
  • It does not know your private data (orders, tickets, code, docs) and its training knowledge is frozen in time.
  • It answers in one shot. It cannot try something, see that it failed, and try again.

An agent fixes all three by wrapping the model in a loop and giving it tools. The model is still just predicting text — but some of that text is a request like "call get_order(1042)", and the surrounding program actually performs it and shows the model the result.

In simple words: an LLM is a brain in a jar. An agent is that brain plus hands (tools), a notebook (memory), and a to-do loop that keeps it going until the job is finished.

The autonomy ladder: LLM → chain → workflow → agent

"Agent" gets used loosely. A useful, widely used distinction (popularised by Anthropic's Building Effective Agents write-up) is:

  • Workflow — LLMs and tools are orchestrated through predefined code paths. You (the developer) decide the steps.
  • Agent — the LLM dynamically directs its own process and tool use. The model decides the steps.
Single LLM callone prompt, one answer → Chain / workflowfixed steps, you decide → Router + toolsLLM picks a branch → AgentLLM decides everything

Moving right gives you flexibility and power, but costs you predictability, speed and money. That trade-off is the central tension of this whole field.

The agent loop

Every agent framework on earth — LangChain, LangGraph, the Claude Agent SDK, the OpenAI Agents SDK — converges on the same core loop. Learn this and you can read any of them.

1. Goal + contextsystem prompt, user message, history, tool list
2. Model decidesanswer now, or ask for a tool?
3. Actyour code runs the requested tool
4. Observetool result is appended to the context
5. Repeat or stopback to step 2 until the model gives a final answer

In code, the whole idea fits in about fifteen lines. This is pseudo-Python — no framework — so you can see there is no magic:

Python (pseudo)
def run_agent(user_goal, tools, max_steps=10):
    messages = [system_prompt, {"role": "user", "content": user_goal}]

    for step in range(max_steps):                 # always cap the loop!
        reply = llm(messages, tools=tools)        # 1. model decides
        messages.append(reply)

        if not reply.tool_calls:                  # no tool wanted => it's done
            return reply.text

        for call in reply.tool_calls:             # 2. act
            result = tools[call.name](**call.args)
            messages.append({                     # 3. observe
                "role": "tool",
                "tool_call_id": call.id,
                "content": str(result),
            })
    return "Stopped: step limit reached"

That is the entire "agent". Everything else you will learn — graphs, middleware, memory, permissions, evals — is about doing this loop safely, durably, cheaply and well.

ReAct: reasoning + acting

The loop above is the practical form of a pattern called ReAct (Reason + Act). The model alternates between a short thought and an action, and each observation feeds the next thought. Modern models do this natively through "tool calling" and often have built-in "extended thinking", so you rarely write ReAct prompts by hand any more — but the name shows up everywhere (e.g. create_react_agent in older LangGraph code).

A full walkthrough: the Acme Support Agent

Here is what the context looks like as the loop runs. Read it top to bottom — each line is something appended to the conversation:

Transcript
USER      Where is order #1042? If it's late, refund me.

ASSISTANT (thinks) I need the order first.
ASSISTANT -> TOOL CALL  get_order(order_id="1042")
TOOL      {"status":"in_transit","eta":"2026-09-28","total":84.50,"carrier":"UPS"}

ASSISTANT (thinks) ETA was Sep 28. Today is Oct 6 -> it IS late. Check carrier.
ASSISTANT -> TOOL CALL  track_shipment(carrier="UPS", order_id="1042")
TOOL      {"last_scan":"Memphis hub, 2026-09-30","delayed":true}

ASSISTANT (thinks) Delayed 8 days, $84.50 < $200 limit -> I may refund.
ASSISTANT -> TOOL CALL  issue_refund(order_id="1042", amount=84.50)
TOOL      {"ok":true,"refund_id":"R-9913"}

ASSISTANT Your order is 8 days late. I've refunded $84.50 (ref R-9913).

Notice what the model did: it chose three tools, in order, based on what each observation said. If the order had been on time, it would have skipped the refund. No developer wrote that if statement — that is what "the LLM directs the flow" means, and it is also why you need evals: you can't read an if statement to know it will behave.

Five workflow patterns worth knowing

Before reaching for a full agent, check whether one of these simpler, more predictable patterns solves the problem. Real systems often combine them.

1. Prompt chaining

Break a task into fixed sequential steps; each LLM call processes the previous output. Add programmatic "gates" between steps to check quality.

Classify email→ Gate: is it a refund?→ Draft reply→ Check tone

Use when the task splits cleanly into steps and you want accuracy over speed.

2. Routing

Classify the input first, then send it to a specialised prompt, tool-set or model. Cheap questions can go to a small model; hard ones to a big model.

RouterLLM classifies→ Billing handler Shipping handler Tech-support handler

3. Parallelization

Run independent LLM calls at the same time and combine them. Two flavours: sectioning (different sub-tasks in parallel) and voting (the same task several times, pick the consensus). Example: one call answers the customer while another, in parallel, screens the reply for policy violations.

4. Orchestrator–workers

A central LLM breaks the task into sub-tasks it figures out at run time, delegates to worker LLMs, then merges results. Unlike parallelization, the sub-tasks are not known in advance. Typical for coding agents ("which files need to change?") and research agents.

5. Evaluator–optimizer

One LLM generates, another critiques, and they loop until the critique passes. Works when you have clear quality criteria — translation, writing, code that must pass tests.

Rule of thumb from the field: start with a single LLM call, add retrieval and examples, then try a workflow pattern, and only move to a true agent when the path genuinely can't be predicted in advance.

Multi-agent systems

Instead of one agent with 40 tools, you can use several smaller agents, each with a narrow job and fewer tools. Common shapes:

  • Supervisor — one "manager" agent routes work to specialist agents (billing agent, shipping agent) and merges the answers.
  • Handoff — the active agent transfers the whole conversation to another agent ("let me hand you to billing").
  • Sub-agent — the main agent spawns a helper with a fresh, clean context window for a side task, and only the short result comes back.

Why bother? Smaller tool lists make tool choice more accurate, and separate context windows stop one long task from drowning the main conversation. Why be careful? Every extra agent multiplies cost, latency and failure modes, and agents can pass each other wrong information. Many production teams start single-agent and split only when evals show a real problem.

When to use an agent — and when not to

  • The number or order of steps can't be known up front (open-ended research, debugging, customer issues).
  • A wrong answer is recoverable or can be checked (tests, human approval, undo).
  • The task is valuable enough to justify extra tokens and latency.
  • The steps are fixed and known — write normal code or a workflow, it will be faster, cheaper and testable.
  • Mistakes are costly and unrecoverable and you have no guardrails or approvals.
  • You need sub-second responses or hard guarantees.
