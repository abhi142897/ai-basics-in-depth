Tool Calling, Context & Memory

Before MCP, LangChain or LangGraph make sense, you need three mechanics firmly in your head: how a model calls tools, how its context window fills up, and how an agent remembers. Every framework in the charter is a convenience layer over exactly these.

If something later in the charter feels like magic, the explanation is almost always on this page.

What the model actually sees

An LLM API is stateless. The model does not remember your last request; on every call you send the entire conversation again as a list of messages. Each message has a role:

RoleWho writes itPurpose
systemYou (developer)Standing instructions: role, rules, tone, policies
userThe personThe request
assistantThe modelIts previous replies — including tool requests
toolYour codeThe result of a tool the model asked for
JSON
[
  {"role": "system", "content": "You are Acme's support agent. Be concise."},
  {"role": "user",   "content": "Where is order #1042?"}
]

The model's reply is a new message you append, then you send the longer list again next turn. Remember this: "memory" in a chatbot is just you re-sending history. It will matter again when we talk about context limits.

Tokens

Models read tokens, not characters or words — roughly ¾ of an English word each. You pay per token, and the context window is measured in tokens. Code, JSON and non-English text usually cost more tokens per idea than plain English.

Tool calling — the 5-step handshake

Here is the single most important mechanic in agent building. The model never runs your code. It only outputs a structured request; your program decides whether and how to run it.

1. You → modelmessages + the list of available tool definitions
2. Model → you"please call get_order with {order_id: 1042}"
3. Your codevalidates the args and actually runs the function
4. You → modelsame messages + a tool message holding the result
5. Model → youfinal text answer (or another tool request → loop)

What step 2 looks like on the wire (shape varies slightly by provider, the idea is identical):

Assistant message
{
  "role": "assistant",
  "content": "",
  "tool_calls": [
    {
      "id": "call_a1",
      "name": "get_order",
      "arguments": {"order_id": "1042"}
    }
  ]
}

And step 4 — you reply with the result, tagged with the same id so the model can match request to answer:

Tool message
{
  "role": "tool",
  "tool_call_id": "call_a1",
  "content": "{\"status\":\"in_transit\",\"eta\":\"2026-09-28\",\"total\":84.50}"
}
Why does it work? Models are trained on huge numbers of examples of "given these tool descriptions and this request, emit a well-formed call". It's still next-token prediction — just very well-trained at producing valid JSON for the schemas you gave it.

Writing a good tool definition

A tool definition has three parts: a name, a description in plain language, and an input schema (JSON Schema) describing the arguments. The model reads all three to decide whether and how to call the tool.

Tool definition
{
  "name": "issue_refund",
  "description": "Refund an order. Use only after confirming the order is late or damaged. Amount must not exceed the order total.",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "description": "Order number, digits only"},
      "amount":   {"type": "number", "description": "Refund amount in USD"},
      "reason":   {"type": "string", "enum": ["late", "damaged", "wrong_item"]}
    },
    "required": ["order_id", "amount", "reason"]
  }
}

Tool-design rules that pay off

  • Describe when to use it, not just what it does ("use only after confirming the order is late").
  • Use enums and clear types to shrink the space of wrong answers.
  • Return short, useful results — big JSON blobs eat your context window (more below).
  • Make error messages instructive: "order not found — ids are 4 digits, did you include '#'?" lets the model self-correct.
  • Don't expose 50 overlapping tools. More tools = more confusion and more tokens. A few well-designed tools beat a big catalogue.
  • Don't make the model juggle opaque IDs it has to guess — return human-readable names alongside IDs.

Parallel calls, tool choice and errors

  • Parallel tool calls — in one turn the model may request several independent calls (e.g. get_order and get_customer). Run them concurrently and return all results.
  • Tool choice — you can usually set it to auto (model decides), required/any (must call some tool), a specific tool, or none. Forcing a tool is how you get guaranteed structured output.
  • Errors are observations. If a tool throws, don't crash the loop — catch it and send the error text back as the tool result. The model will often fix its own arguments and retry.
Python
def execute(call, tools):
    try:
        fn = tools[call["name"]]
        return str(fn(**call["arguments"]))
    except KeyError:
        return f"Error: unknown tool {call['name']!r}"
    except TypeError as e:                 # bad / missing arguments
        return f"Error: invalid arguments - {e}"
    except Exception as e:                 # the tool itself failed
        return f"Error: {e}"

Structured output

Often you don't want a chat reply — you want data your code can parse: {"intent": "refund", "order_id": "1042"}. Three ways, from weakest to strongest:

  1. Ask nicely ("reply in JSON") — works until it doesn't. Avoid in production.
  2. Force a tool call whose schema is your output shape.
  3. Provider-native structured output — the API constrains generation to a JSON Schema.

In frameworks you usually write a Pydantic class and the library picks the best strategy for you (LangChain does exactly this with response_format — see Topic 04). Always validate the result anyway; if it fails, send the validation error back to the model and let it retry once.

The context window — your agent's RAM

The context window is the maximum number of tokens the model can consider in a single call: system prompt + all messages + tool definitions + tool results + the reply it is writing. Think of it as RAM, not a hard disk: fast, precious and finite.

System prompt~1–3k+ Tool definitions~0.2–1k each+ History + tool resultsgrows every step= Context windowhard limit

In agents, the thing that fills the window is almost always tool results: a 5,000-row SQL result, a whole web page, a 2,000-line file. And there is a second, subtler problem — context rot: as the window fills up, models get measurably worse at recalling and using information buried in the middle, even before the limit is reached. A bigger window helps, but "put everything in" is not a strategy.

TechniqueIdeaAcme example
Truncate tool outputCap size, return a preview + "N more rows"Return the last 5 orders, not 500
Clear old tool resultsDrop stale observations once usedDelete raw carrier JSON after reading it
Summarise / compactReplace old turns with a short summary"Customer is angry; order late; refund pending approval"
Offload to files / notesWrite facts to disk, re-read when neededSave case notes to notes.md
Just-in-time retrievalKeep references (IDs, paths), fetch details on demandHold order IDs; call get_order only if needed
Sub-agentsDo heavy work in a separate window; return a digestA "policy lookup" agent returns 3 lines, not the handbook

Managing this deliberately is called context engineering, and in a production agent it is the harness's job — Topic 06 goes deep.

Prompt engineering vs context engineering

Prompt engineering is writing good instructions. Context engineering is the bigger question: of everything that could be in the window right now, what is the smallest set of high-signal tokens that gets the right behaviour?

A solid system-prompt skeleton

System prompt
# Role
You are Acme's customer support agent.

# Goals
Resolve order problems quickly and politely.

# Rules
- Never promise a refund before checking the order status.
- Refunds over $200 require human approval (use request_approval).
- If you are unsure, ask one clarifying question.

# Tools
- get_order: look up an order by id. Use first for any order question.
- issue_refund: refund an order. Only after verifying it is late/damaged.

# Style
Short, friendly, no jargon. End with the next step for the customer.
  • Be specific and direct; explain why a rule exists — models follow reasoned rules better.
  • Show 2–3 diverse, canonical examples rather than a laundry list of edge cases.
  • Don't hard-code brittle if-else logic in prose — if it must always happen, enforce it in code (the harness), not the prompt.

Memory: short-term vs long-term

Because the API is stateless, "memory" is something you build. There are two kinds:

Short-term (thread) memoryLong-term memory
ScopeOne conversation / one task runAcross conversations and days
What it holdsThe message history and working stateFacts, preferences, past outcomes, learned procedures
How it's storedCheckpointed state keyed by a thread/session idA database, key-value store or vector store
Acme example"The order we've been discussing is #1042""This customer prefers email, was refunded twice before"
In LangGraphCheckpointer + thread_idThe Store interface

Long-term memory is often split by kind: semantic (facts about the user), episodic (what happened last time), and procedural (instructions the agent has learned — effectively an evolving system prompt). Two hard design questions: what deserves to be saved (not every message), and when to write it — during the conversation ("hot path") or in a background job afterwards.

RAG — retrieval-augmented generation

The model doesn't know your handbook, tickets or code. RAG fixes that by fetching relevant text at question time and putting it in the context.

Documentspolicies, FAQschunk → Chunks~200–800 tokensembed → Vector storesearchable by meaningtop-k → Promptquestion + best chunks

Embeddings turn text into number-vectors so that text with similar meaning lands close together; the question is embedded too, and the nearest chunks are retrieved. Classic RAG retrieves once, up front. Agentic RAG makes retrieval a tool (search_policies(query)), so the agent decides when to search, rewrites poor queries, and searches again if the first result was thin. Most modern agents work this way — and MCP (next topic) is a standard way to plug such a search tool in.
